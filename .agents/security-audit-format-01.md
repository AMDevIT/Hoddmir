# Security audit and format 0x01 hardening

- Objective and status. Audited the record format, storage, key handling, and AEAD providers. Implemented the fixes in the current development format 0x01. Earlier development vaults need to be recreated. There is no migration path.
- Decisions. Each record authenticates its absolute offset and the preceding serialized record digest. The first record binds the encrypted header and session salt. The header and DEK wrapper authenticate separate context labels. The public checkpoint API supports detection of valid older histories when the application keeps the checkpoint in trusted external storage.
- Persistence. A store holds an exclusive lease on its backend object. The file backend holds a sibling lock across replacement. Reads distinguish absent IDs from corrupt indexed records. Verification checks the committed head, omits plaintext IDs from logging, and stops at the first broken chain link. Recovery can compact an incomplete tail when the trusted checkpoint matches the last complete record.
- Key handling. Bounded authenticated DEK KDF parameters, cleared additional temporary key material, and corrected the AES-CTR + HMAC guidance on public HKDF salts and weak keys.
- Affected files. Core storage and crypto providers, Bouncy Castle providers, MSTest and the console fixture cleanup, README.md, and CHANGELOG.md.
- Checks. Restored and built the solution on Windows. MSTest passed 164 cases on .NET 9 and 164 on .NET 10. The attack harness rejected same-offset splices on file with all four AEAD providers, rejected 49,008 single-bit mutations, classified 6,118 truncation points, and rejected record reordering. It also verified writer exclusion, live truncation detection, corruption errors and log redaction. The mutation matrix used a test-only KDF with the real AEAD providers. The file replay and offline password checks used Argon2id. NuGet reported no vulnerable direct or transitive packages at the time of the check.
- Open issues. A copied valid vault still permits offline password guesses at the outer header cost. Rollback protection across reopen requires a trusted checkpoint outside the vault. Runtime verification covered Windows. The next step for release is to exercise file replacement and durability on supported Unix platforms and obtain independent cryptographic review.
